# synchronized와 임계 영역 복습

> 공유 자원을 여러 스레드가 함께 수정할 때 왜 문제가 생기는지와 임계 영역을 보호하는 방법을 정리했다.

## 1. 검증과 변경 사이의 틈

계좌 인출 로직을 생각해 보자.

```text
if (balance < amount) {
    return false;
}

balance = balance - amount;
return true;
```

두 스레드가 같은 계좌에서 동시에 실행하면 둘 다 변경 전 잔액을 보고 출금 가능하다고 판단할 수 있다.

```text
초기 잔액 1,000

A → 1,000 확인, 출금 가능
B → 1,000 확인, 출금 가능
A → 800 차감
B → 800 차감
```

`volatile`로 최신 잔액이 보이게 하더라도 검증부터 차감까지의 전체 과정이 하나로 보호되지는 않는다.

## 2. 경쟁 상태

다음 조건이 겹치면 동시성 문제를 의심해야 한다.

- 여러 스레드가 같은 데이터를 사용한다.
- 하나 이상의 스레드가 값을 수정한다.
- 결과가 실행 순서에 따라 달라진다.

공유 데이터의 결과가 스레드 실행 순서에 의존하는 상황을 경쟁 상태로 볼 수 있다.

## 3. 임계 영역

다른 스레드가 중간에 개입하면 안 되는 코드 범위를 임계 영역이라고 한다.

계좌 예제에서는 다음 세 단계가 하나의 단위여야 한다.

```text
잔액 확인
→ 출금 가능 여부 판단
→ 잔액 변경
```

## 4. `synchronized` 메서드

```java
public synchronized boolean withdraw(int amount) {
    if (balance < amount) {
        return false;
    }

    balance -= amount;
    return true;
}
```

인스턴스 메서드의 `synchronized`는 해당 객체의 모니터 락을 사용한다. 같은 객체에 접근하는 다른 스레드는 락이 반환될 때까지 기다린다.

서로 다른 계좌 인스턴스라면 락도 서로 다르므로 동시에 작업할 수 있다.

## 5. 락의 흐름

```text
A가 락 획득
→ 임계 영역 실행
→ 메서드 종료와 함께 락 반환
→ B가 락 획득
→ 변경된 상태를 기준으로 다시 검증
```

정상 반환이나 예외 발생으로 블록을 벗어나도 JVM이 모니터 락을 반환한다.

## 6. 동기화 범위 줄이기

메서드 전체가 공유 상태를 다루지 않는다면 필요한 부분만 잠글 수 있다.

```java
public boolean withdraw(int amount) {
    log("거래 시작");

    synchronized (this) {
        if (balance < amount) {
            return false;
        }
        balance -= amount;
    }

    log("거래 종료");
    return true;
}
```

락과 관계없는 작업까지 직렬화하면 처리량이 줄어든다. 다만 보호해야 할 검증과 변경을 따로 떼어 놓으면 다시 안전성이 깨질 수 있다.

## 7. `count++`

```text
count++;
```

한 줄이지만 원자적이지 않다.

```text
현재 값 읽기
→ 1 증가
→ 결과 저장
```

두 스레드가 같은 값을 읽으면 증가 한 번이 사라질 수 있다.

## 8. 지역 변수

일반적인 지역 변수는 각 스레드의 스택 프레임에 따로 존재한다.

```java
void calculate() {
    int localCount = 0;
    localCount++;
}
```

하지만 지역 변수가 가리키는 객체가 공유 객체라면 그 객체의 내부 상태는 여전히 동기화 대상이 될 수 있다.

## 핵심 정리

- 최신 값이 보이는 것과 복합 연산 전체를 안전하게 수행하는 것은 다르다.
- 임계 영역은 다른 스레드의 중간 개입을 막아야 하는 범위다.
- `synchronized`는 객체의 모니터 락을 이용한다.
- 공유 상태와 무관한 작업은 가능하면 락 밖에 둔다.
- 공유 필드의 `count++`는 원자적이지 않다.

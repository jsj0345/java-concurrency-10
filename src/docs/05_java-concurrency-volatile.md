# volatile과 메모리 가시성 복습

> 한 스레드가 수정한 값이 다른 스레드에서 바로 보이지 않을 수 있는 이유와 `volatile`이 해결하는 범위를 정리했다.

## 1. 공유 플래그가 예상대로 바뀌지 않는 상황

```java
class Task implements Runnable {

    boolean running = true;

    @Override
    public void run() {
        while (running) {
            // 반복 작업
        }
    }
}
```

`main` 스레드가 `running = false`로 바꾸더라도 작업 스레드가 이전 값인 `true`를 계속 관찰할 수 있다.

같은 객체를 참조하고 있다는 사실만으로 모든 스레드가 항상 같은 값을 즉시 본다고 가정할 수 없다.

## 2. 메모리 가시성

CPU는 메인 메모리 접근 비용을 줄이기 위해 캐시와 여러 최적화를 사용한다.

개념적으로 보면 다음처럼 서로 다른 값이 관찰될 수 있다.

```text
main이 보는 running   → false
worker가 보는 running → true
```

한 스레드의 변경이 다른 스레드의 읽기에 언제 반영될지 확실하지 않은 문제가 메모리 가시성이다.

실행할 때마다 잘 끝났다는 결과만 보고 안전하다고 판단하면 안 된다.

## 3. `volatile`

```java
class Task implements Runnable {

    private volatile boolean running = true;
}
```

`volatile` 필드의 읽기와 쓰기에는 스레드 사이의 가시성 규칙이 적용된다. 한 스레드가 값을 변경하면 다른 스레드도 그 변경을 관찰할 수 있도록 보장된다.

종료 요청이나 설정 변경처럼 값 하나의 최신 상태가 중요한 경우에 사용할 수 있다.

## 4. 해결하지 못하는 문제

```text
count++;
```

이 연산은 다음 단계로 나뉜다.

```text
count 읽기
→ 1 더하기
→ count에 저장
```

`count`에 `volatile`을 붙여도 두 스레드가 같은 값을 읽고 같은 결과를 저장할 수 있다. 따라서 복합 증가 연산의 원자성까지 보장하지는 않는다.

## 5. 가시성과 원자성

| 문제 | 의미 | 해결 방향 |
|---|---|---|
| 가시성 | 다른 스레드의 변경이 보이지 않음 | `volatile`, 락 |
| 원자성 | 여러 단계 사이에 다른 스레드가 개입 | `synchronized`, `Lock`, 원자 클래스 |
| 순서 | 읽기와 쓰기 순서가 예상과 달라질 수 있음 | 동기화 규칙 |

`volatile`은 중요한 도구지만 모든 동시성 문제를 해결하는 키워드는 아니다.

## 6. 적합한 사용 조건

```java
private volatile boolean shutdownRequested;
```

다음 조건이라면 사용 목적이 비교적 분명하다.

- 여러 스레드가 같은 필드를 읽거나 쓴다.
- 가장 최근 값이 보여야 한다.
- 변경이 단순 대입 수준이다.
- 여러 필드를 한 묶음으로 일관되게 바꿀 필요는 없다.

여러 값이 함께 맞아야 하는 복합 상태는 락이나 불변 객체 교체 같은 별도 설계가 필요하다.

## 핵심 정리

- 같은 객체를 공유해도 최신 값이 즉시 보인다고 가정할 수 없다.
- 메모리 가시성은 한 스레드의 변경을 다른 스레드가 관찰하는 문제다.
- `volatile`은 공유 값의 읽기와 쓰기에 가시성을 제공한다.
- `count++` 같은 복합 연산은 `volatile`만으로 안전해지지 않는다.
- 가시성과 원자성은 구분해서 해결해야 한다.
